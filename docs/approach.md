

# Technical Approach

## Goal

The goal of this prototype is to help a lending analyst complete an initial residential comparable-sales review faster. The tool is not designed to replace formal appraisal or underwriting judgment. It is designed to make the first pass of comp analysis more structured, explainable, and repeatable.

The core workflow is:

```text
Subject property input
    -> candidate comparable search
    -> deterministic comp scoring
    -> weighted valuation estimate
    -> confidence and risk flags
    -> underwriting-style memo
```

## Scope

The project focuses on Alberta residential properties. The supported property types are:

- Detached
- Semi-Detached
- Townhouse
- Duplex
- Condo

I intentionally kept the scope residential and Alberta-focused because the challenge asked for good judgment and a focused agent that works. Commercial real estate would require different comp attributes, income metrics, lease data, cap rates, and market assumptions, so I left that as a future extension.

## Data design

The app uses a synthetic Alberta residential sales dataset generated by `scripts/generate_synthetic_data.py`.

The dataset is intentionally structured as a flat table rather than nested JSON because tabular property records are easier to validate, filter, score, display, and eventually replace with real transaction data.

Important fields include:

- Location: city, neighborhood, latitude, longitude
- Property details: property type, bedrooms, bathrooms, living area, lot size, year built
- Sale data: sale date and sale price
- Condition/features: condition, garage spaces, finished basement, renovation flag, transit proximity, and park adjacency

The synthetic generator uses market-like assumptions such as city multipliers, neighborhood premiums, property-type price-per-square-foot baselines, condition multipliers, feature adjustments, and random noise. It also creates some missing values in optional fields such as lot size and year built so that the app can demonstrate graceful handling of imperfect data.

## Candidate search

The comp search is staged. The agent starts with the strongest possible comp pool and only broadens the search when there are not enough candidates.

Search stages:

1. Same neighborhood, same property type, recent sales
2. Same city, same property type
3. Same city, wider property/date range
4. Nearby Alberta markets
5. Broad Alberta fallback

This design prevents hard failure in sparse markets while still making it clear when confidence should be reduced. The search stage also produces a user-facing message so the analyst understands how far the agent had to broaden the comp pool.

## Scoring model

Each candidate comp is scored from 0 to 100 using deterministic rules.

| Factor | Weight | Reason |
|---|---:|---|
| Location similarity | 30% | Location is usually the strongest driver of residential comparability. |
| Property type match | 20% | Detached homes, condos, and townhomes should not be treated as equivalent. |
| Living area similarity | 15% | Size materially affects value and price-per-square-foot interpretation. |
| Bedroom/bathroom similarity | 10% | Functional similarity matters for residential demand. |
| Year built similarity | 10% | Age can proxy for construction era and condition. |
| Sale recency | 10% | Recent sales are more reliable in changing markets. |
| Feature similarity | 5% | Features help explain adjustments but should not dominate the score. |

The scoring model is intentionally simple and inspectable. It is not meant to be the final underwriting model; it is a practical first-pass ranking engine that can be tuned with analyst feedback.

## Valuation method

The valuation engine uses the top-ranked comparable sales and calculates a weighted price-per-square-foot estimate.

Higher-scoring comps receive more influence. The app then multiplies the weighted price per square foot by the subject property's living area.

```text
weighted_ppsf = weighted average(top_comp_price_per_sqft, comp_score_weight)
base_estimate = weighted_ppsf * subject_living_area
```

The output is a range rather than a single exact number. The range is wider when confidence is lower.

This is more appropriate for underwriting support because it avoids false precision.

## Confidence and risk flags

Confidence is based on:

- Average quality of the selected comps
- Number of selected comps
- Sale recency
- Property-type similarity

The confidence label is one of:

- High
- Medium
- Low

The valuation result also includes risk flags such as:

- Fewer than five comparable sales were available
- Some comps are outside the subject's immediate location
- Some comps differ from the subject property type
- Selected comps have meaningful size differences
- Some comps are older sales
- Subject year built or lot size is missing

This makes the output more useful for human review because it explains not only what the estimate is, but how much trust the analyst should place in it.

## LLM layer

The LLM is optional and is used only for communication.

The deterministic engine produces:

- Ranked comps
- Score breakdowns
- Valuation range
- Confidence
- Risk flags

If an `OPENAI_API_KEY` is configured and the user enables the LLM option, the app passes those structured results to the LLM and asks for a concise underwriting-style memo.

The LLM is not allowed to choose comps, calculate the estimate, override the valuation, or invent market facts. If the API key is missing or the LLM call fails, the app returns a rule-based memo instead.

This separation is important because comp analysis in a lending context should be repeatable and auditable.

## Reliability and graceful failure

The app is designed to degrade gracefully:

- If no tight neighborhood comps are available, the search expands to same-city comps.
- If same-property-type comps are sparse, the search expands to similar residential properties.
- If local markets are sparse, the search expands to nearby Alberta markets.
- If optional subject fields are missing, the valuation still runs and adds risk flags.
- If the LLM fails, the rule-based memo is returned.
- If the dataset is missing required columns, the loader raises a clear error.

The system avoids returning fake precision by showing confidence and a range.

## Key tradeoffs

### Synthetic data

Synthetic data was used because the brief allowed it and because reliable public sold-price data is not always easy to access. The schema is designed to make replacement with real transaction data straightforward.

### Deterministic valuation

I chose a deterministic scoring and valuation engine rather than letting an LLM perform the valuation. This makes the result easier to inspect, test, and audit.

### Streamlit UI

Streamlit was chosen because it is fast to ship, easy to review, and sufficient for a hackathon prototype. The business logic is still separated into reusable Python modules so the UI can be replaced later if needed.

### No commercial workflow in MVP

Commercial lending comp analysis would require a meaningfully different dataset and valuation method. I kept the MVP focused on residential properties and listed commercial borrower support as a future extension.

## Future improvements

If this were expanded beyond a prototype, the next steps would be:

- Replace synthetic data with real internal or MLS-style transaction data
- Add geospatial distance scoring using actual coordinates and travel distance
- Add market time adjustments for older sales
- Add more detailed renovation and condition adjustments
- Learn scoring weights from analyst feedback
- Support exportable valuation memos
- Add saved analyses and audit trails
- Add commercial property workflows using income and cap-rate data
